## 评论监听

每60秒轮询当前监听账号网页端“评论和@”通知，读取分页，按账号+comment ID去重。按通知时间降序到达监听起点后停止翻旧记录，不把首次开启之前的历史通知算作新积压。只接收启用后出现的有效评论：自己笔记的留言，或其他笔记中对小桃评论的回复。后一种必须确认被回复评论的作者确实是小桃。点赞、关注、仅@、失效内容、未知目标、自己发出的内容均不触发公开回复。

通知原始目标由执行器绑定，模型只能输出reply/no_reply/stop及文字，不可指定账号、笔记或收件评论。模型收到评论、被回复文字、笔记标题及已经发送记录；无足够事实不能编答案。明确停止回复会持久停止对该用户的回复。两种方向都按原通知的comment ID回复，而非只挂在一级评论下。

只排除小桃自己和配置中明确登记的自动评论账号（`automated_commenter_ids`），避免自动互聊；工作台里登录过的其他人工账号仍正常接收留言。此前把全部管理账号排除，导致Leo发的“优秀👍”漏处理，已纠正并补收通知；随后接收方复核发现回复仅小桃自己可见，不能把发送成功或发送方读到记录当成对方可见。首次普通善意留言应简短回应，广告、重复刷屏或明确收尾才考虑no_reply，模型判断原因保留在台账。未知评论发送回执不自动重试。

提交返回comment ID只记`submitted`。后台每分钟用账号2及独立核验账号1读取原帖，对照回复ID、作者、原通知目标和最终文字；独立账号读到且状态正常才记`replied`。账号1与留言者匹配时注明接收方核验，否则只能说独立账号可见，不能保证接收方通知送达。独立账号必须属于同一工作台用户，并校验实际身份；配置键为`comment_visibility_account_id`和`comment_visibility_external_user_id`，不向任务或前端暴露凭据。仅发送方可见或读不到时记`not_visible`，读取失败只记待核对，不能判定平台处罚。按用户要求，可见性异常只提示和只读复查，后续新评论继续自动回复，不因上一条尚未核验或不可见而全局暂停。已提交的评论不重复发送；身份不匹配、真实网络故障、用户主动暂停等独立检查继续生效。不切换出口或账号规避限制。

### Agent 直接发布与续登后的状态回填

`content-automation.json` 的 `post_execution=agent` 表示由 Agent 使用工作台的发布接口执行，不再进入旧的 post JSON / Pexels 候选下载器。创建发布任务时传入 `multica_issue_id`（UUID），该字段保存在 `PublishJob.publish_options`，重复提交同一账号和 issue 会返回原发布任务。没有关联时只等待，不按标题猜测归属。

跟踪器核对工作台所有者、Creator 身份、原 issue 负责人后，从持久化发布结果回填：等待登录/平台失败/回执未确认映射为 blocked，实际 published 且有笔记ID才映射 done；状态写入使用 suppress_run，避免又唤醒创作 Agent 重发。同步失败保留非终态下轮继续。账号中心处理实际上传 906 事件，登录核验后原 waiting_login 发布任务由既有 publish_recovery 恢复；仅上传或仅起草不授权新发布，uncertain 不自动重发。

### 原始 Prompt 下的成稿接入

`native_artifact_intake=true` 时，已完成的指定 Agent 在当前 issue 同一评论中附上 `note.md`（首行为标题、空行后为正文）及最终图片，程序将它们保存为关联该 issue 的持久化发布任务；无需把接口字段写进用户的创作 Prompt。只接收当前负责人 Agent 的附件与已结束的最新执行，不处理已取消/已完成 issue。实际发稿仍由发布 API 和恢复队列执行。已经关联但被删除的发布记录不自动重建。

待处理记录必须同时带有自动发布授权标志和 issue 关联，恢复队列才执行第一次上传；普通草稿和手工 pending 任务不会因该扫描自动发布。素材写入并落库发生在平台上传之前，预检查失败后仍可继续原稿。图片转为 JPEG 供原上传器使用，原附件保留。
