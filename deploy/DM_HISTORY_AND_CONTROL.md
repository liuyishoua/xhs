# 私信上下文与发送控制

2026-10-24：平台历史中 `content_type=0` 且 `content=""` 的空占位记录不属于聊天，不能据此判断“主人已回复”。分页游标仍计入这些传输记录；非空未知类型和真实图片/文字继续保留。重新同步可将旧误收条目标记为 `source=placeholder` 并从聊天视图排除，Channel 已同步记录通过递增版本的逻辑删除更正，旧不可变快照与本地审计行保留。回归使用合成历史和假平台适配器，不向真人发送验收消息。

账号主人可在单个 `DmConversation.session_state.reply_goal` 保存 `status=active` 的会话指示。仅该账号/对方的后续回复任务取得 `owner_goal`，不修改其他联系人或全局 Agent 指令；任务完成或撤销时将状态改为非 active。

## 账号控制方式

每个监听账号独立保存 `control_mode`，修改后点击“应用回复配置”。发送开关独立控制是否真的发送。

| 控制方式 | 行为 |
| --- | --- |
| 请求批准 `request_approval` | 模型自行决定回复或不回复；有回复时显示“待批准发送”，账号主人点击“批准发送”后才可发送。 |
| 帮我批准 `auto_approve` | 模型直接决定普通聊天的回复；只有确需本人决策的特殊事项进入待处理。迁移默认采用此方式。 |
| 完全访问 `full_access` | 模型自主回复或不回复，不等待人工批准。没有可直接发送的合法结果时不发送。 |

权限只覆盖当前账号的一对一私信；不会扩大 Multica 的平台工具权限。任务只返回结构化决策，XHS 工作台绑定账号、收件人并检查发送开关。三档均保留匹配发送回执的校验；回执不确定时不盲目重发。

批准绑定当前 Channel 消息 ID。重新分析、变更控制方式或收到更新消息会使旧正文/旧批准失效。模型处理中变更控制方式，会等待该轮 Channel 完成后按新配置重新分析。停止监听或关闭发送开关后不会发送。

## 最近 24 小时的双向历史

每条新私信提交模型前，通过账号自身的签名请求分页读取 `/api/im/web/messages/history`，获取同一账号与同一用户过去 24 小时的双向聊天。完整覆盖范围和最新消息序号持久化到 SQL，后续只补增量；刚同步且覆盖当前消息的缓存直接复用。历史仅作为上下文，不触发回复；自己的实时消息和成功回执也写入历史。

数据库仍为工作台原 SQL 数据库，新增：

- `xhs_dm_history`：以账号、对方用户、平台消息 ID 去重，保存方向、文字、类型、撤回状态和真实发送时间。
- `xhs_dm_conversations`：保存该会话同步范围、完整性，以及模型最近的意图、风格、关系进展、决策摘要。
- 原 `xhs_direct_messages` 保留每次触发及不可变的 Channel 上下文快照、历次分析和发送回执。

页面“查看一天聊天”展示双方消息和最新分析。非文字历史保留类型占位，撤回内容不作为可见正文。查询和批准操作均验证账号归属。

每页最多 100 条，单轮最多 30 页；超出上限或分页不完整时暂停本轮分析并显示同步错误，30 秒后重试，不把部分数据冒充完整历史。SQL 保存完整读取内容；传给 Channel 的上下文受其大小限制，只保留最近可容纳内容并明确标记截断、总条数和纳入条数。旧记录不因超出一天窗口而从数据库删除。

连续到达的私信合并到最新一条判断。Channel 运行中的旧轮先等待完成，再丢弃过时回复；发送原子检查也拒绝给已有更新消息的旧轮发送。如果本账号在生成期间手动回复，重新同步和判断，避免重复接话。超过 5 分钟的待发送或待批准正文重新分析。

模型返回 `decision=reply|no_reply|handoff`，`reply_messages` 包含按顺序发送的1至4条最终气泡，支持文字和真实媒体；旧版单条 `reply_text` 继续兼容。意图、风格、依据单独保存，不发给对方。普通寒暄、简短肯定无需默认转人工。明确不回复进入 `skipped`；合并旧消息进入 `superseded`。原版本缺少历史而挂起的记录会补充历史重新分析；有新消息时旧记录自动合并。

## 自然对话与主动表情（2026-10-10）

交流方式以 [xhs-natural-expression](../../agent-tools/xhs-natural-expression/SKILL.md) 为主规范；公开微信私聊、评论互动与研究依据见其 [research.md](../../agent-tools/xhs-natural-expression/references/research.md)。普通私聊不默认套恋爱或客服流程。Agent 管任务读取边界，任务单管快照及输出契约，Skill 管接话和表达，不在多层反复堆叠“温柔、关怀、关系进展”。

短版 Skill 主体由发布脚本直接提取并附上 SHA256，写入路由指令；每张新任务通过不可变路由快照取得对应版本。不依赖“文件已挂载”推断本轮已加载，不要求重复读取同一主体。详细情境、研究与 GIF 运行约束仍按需从挂载引用取得。

`context.dialogue_state` 按本会话成功发送凭据标记 `known_automated_message_ids`，包含同一主人管理的对端账号在这段对话中的已确认自动回复。标记内容仍是聊天事实，但不是主人风格正例；`self_style_candidates` 只表示来源未确认，不能认定是人工。该元数据不修改 Channel 历史身份、修订号或已提交快照。

纯文字来话也可以获得本账号已准备、实际存在本地文件的反应图库候选。当前图片优先，保留少量最近图片，另提供最多4张反应候选，总附件仍最多8张。候选按当前文字粗排；近期已发的图片不再作为新的图库候选。它们仍可作为聊天历史附件供理解，最终是否再次发送由 Skill 结合上下文判断。账号之间不共享资产 ID。没有本地文件的旧库记录不自动联网取图，不重新开放已删除的素材管理接口。

catalog 标明 `source=current|conversation|reaction_library` 和 `image_number`。模型需要通过真实图像工具查看下载后的附件；下载或 Markdown 地址本身不算看图。GIF 表情用 `type=sticker`，保留原生 `content_type=16`、`isGif=1`；普通照片才用 `image`。图库读取/上传故障仅使该候选不可选，普通文字回复仍可继续；当前来话图片读取失败仍明确失败，不能假装看过。

gifgrep 已安装，但当前0.4.4联网搜索需要 GIPHY/KLIPY 服务配置，不能沿用旧版 Tenor demo-key 假设。现成账号 GIF 不需要在线搜索密钥。没有合适图时回文字，不用固定发图比例；对方明确不要图片时尊重其偏好。

相关回归：私信、会话与新增来源/表情链路共93项通过、1项跳过；Channel 119项通过。真实 Multica 回归使用原创合成多轮场景；报告与 issue/run ID 在 Channel 私有 `.local/dialogue-evaluation-*.json`。隐藏语义标签、随机 ID 和调整图片顺序用于检查实际选图，不依赖标签。发送格式与匹配回执使用假传输验证，未向真实社交用户发送测试。

## 页面手动聊天

侧栏“私信聊天”位于 `/platforms/xhs/chat`，支持选择 PC 账号、会话搜索、打开主页链接对应的新会话、最近 24 小时双向记录，以及文字、Unicode 表情和单张图片发送。私信监听记录也提供“打开聊天”入口。账号选择和 URL 中的会话可在刷新后恢复；状态轮询只读本地 SQL，不重复向平台拉全部会话。

手动连接与自动监听独立。后台复用同一账号的 WebSocket；仅开启手动聊天时只归档收到的消息，不创建模型任务。刷新会话读取摘要，打开或同步某个会话只按该会话持久化断点补收。

`xhs_dm_manual_messages` 在发出前保存客户端请求 ID、绑定的平台身份、文字或账号所属图片、唯一发送 mid 和状态。相同账号同一客户端请求 ID 重交返回原记录，改变内容则拒绝。发送必须取得匹配 mid、整数 code=0 且 msg=ok 的平台回执；超时、丢失回执或进程重启中的 sending 进入 uncertain，不自动重发。同会话后续手动发送等待核对，其他会话继续。图片先保存到账号私有素材目录，明确发送时才上传到平台。

手动发送仅取消当前会话尚未发出的旧自动回复，不开启人工接管；后续新消息仍按账号的自动回复设置处理。只有用户点击“手动接管”才暂停此会话的自动回复，接管期间新消息继续归档。页面可恢复自动回复，但有待发送、正在发送或待核对的手动消息时不能交回模型。模型领取发送任务时再次检查人工接管与手动 outbox，避免并发插话。人工确认收到只记录人工确认，不伪造平台成功回执。

接口前缀 `/api/xhs/chat`：GET conversations/messages；POST accounts/{id}/connect、refresh、send、images、control；GET requests/{client_id}；POST requests/{id}/resolve。接口始终校验工作台账号归属，手动发送还复核绑定的平台用户 ID，图片只允许使用当前账号素材。

验证使用临时 SQL、合成 Socket/平台回执和浏览器拦截的模拟会话，不给真实联系人发送验收消息。

2026-10-13 部署验证：相关后台回归 173 项通过，TypeScript/Vite 生产构建通过；浏览器 11 项场景通过，覆盖文字/图片、重复提交抑制、响应丢失不重发、延迟响应下草稿保护、账号切换与刷新恢复、移动布局。线上迁移版本 b7a318c49d21，手动发送表与手动连接开关均为 0，确认模拟验证未触发真实发送或连接。

## 即时私信优化（2026-10-14）

连续在线且当前会话已完成补收时，从 SQL 双向记录扩展历史覆盖，不为每条消息再次请求平台历史。断连、历史缺口、过期覆盖或明确刷新仍执行平台同步；未完成补收的会话保持阻塞。连续消息合并等待为0.5秒，工作循环0.2秒；Channel 即时回复取消额外合批等待并每0.2秒检查返回结果。receipt.timing 记录历史耗时、历史来源和提交时间。

leo 和小桃的私信分别绑定独立的 GPT-6 Luna low/priority 回复 Agent。账号档案与对话能力预加载，完整的 Channel 冻结快照直接进入 Multica Chat，不再让模型查询 issue、评论或重复读取技能。每轮隔离，完成归档；创建/提交仍有持久化意图和回执核对，实际平台发送、人工接管、主人已接话检查和去重仍由工作台执行。文字任务不调用工具；图片必须实际查看才可采用。创作、评论和研究的原 Agent 不改动。

部署脚本：`deploy/fast_reply_agents.py` 安装/更新专用 Agent，`deploy/activate_fast_reply.py` 保存原绑定并切换两个现有账号的私信路由；备份与报告位于私有 `.local/fast-reply`。这两个脚本通过 Channel Store 操作，需要当前工作台环境有 Flask（同 Channel 的运行依赖）。运行时无需这项跨项目脚本依赖。

`CONFIG_FILE=.local/runtime.yaml PYTHONPATH=.:deploy .venv/bin/python deploy/benchmark_fast_reply.py --persona xiaotao --worker --count 5` 使用隔离 SQL、合成双向历史、真实 Multica 模型和模拟平台 ACK；不会发送真实社交消息。15个样例含闲聊、后续问题、明确停止和未知身份，平均5.429秒，范围3.696–7.689秒；其中10个经过完整工作台调度、发送前检查和模拟ACK，5个测到回复就绪。历史准备5.85–23.58毫秒，全部0次工具调用，输出契约全部有效。真实平台网络回执耗时没有计入这些样例，不将测试结果当作任何网络状态下的送达保证。
# 发布与续登恢复契约（2026-10-14）

发布页的图片上传和发布前上传失败均上报 `creator_upload` 状态及平台业务码；旧登录请求不得覆盖新登录态。906 由账号中心识别为需要重新登录的创作者上传故障，仅在已绑定并启用短信恢复时自动执行一次，随后核验身份与上传权限。其余风险不冒充登录过期。

已明确发起的发布任务在发送前遇到 906/-100 后保存为 `waiting_login`，保留原稿、素材、目标账号与授权，后台等待账号核验恢复后继续一次。仅上传图片不会授权发布。取消、账号或所有权变化会阻止恢复；发送回执丢失或在途重启转为 `uncertain`，不自动重复发帖。前端显示等待续登、恢复发布和待核对状态。
